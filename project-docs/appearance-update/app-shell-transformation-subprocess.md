## Acceptance Criteria

- The implementation is traceable to the approved outputs of lifecycle points 1–3. It adapts the reference without copying its branding or product structure and does not silently decide questions those inputs leave unresolved.
- `/`, `/pipeline`, and `/replay` use the mapped near-black editorial surfaces, warm-gold emphasis, typography, borders, spacing, and effects through shared semantic tokens or components. No new route-local literal color, color-bearing shadow, corner-radius, or motion value is introduced for a shell concern.
- `/pipeline` and `/replay` use the same transformed rail and top bar. Exactly the matching navigation item is exposed as current after a direct load and client-side navigation; the breadcrumb matches the active route; responsive labels or tooltips remain available; and both rail and top-bar contact controls open the same dialog.
- The standalone `/` boot frame visually belongs to the same system without being moved into `_app`. Its timed boot log remains readable, and both **Initialise** and Enter continue to navigate to `/pipeline`.
- Shared heading and control primitives—including `SectionHeader`, buttons, icon controls, tabs, switches, and tooltips—have consistent and clearly distinguishable treatments for every applicable state: default, hover, focus-visible, pressed or active, selected or current, and disabled. Existing keyboard activation, tab and switch semantics, accessible names, and focus-visible behavior remain intact.
- The contact dialog has an accessible name, traps focus while open, closes with Escape and its close control, and returns focus to the exact rail or top-bar control that opened it. Submitting the existing contact form still closes the dialog and raises its success toast.
- Toasts and other shell-level feedback remain readable against the transformed surfaces, retain non-color status cues and live-region behavior, preserve the existing automatic timeout, and can be manually dismissed where currently supported. The toast stack and dialog remain above shell and route content without obscuring their own essential controls.
- Browser checks cover `390×844`, `700×900`, `900×900`, and `1440×900`, exercising the current below-540px, 540–849px, 850–1099px, and 1100px-or-wider regimes. At each size, the rail, top bar, route frame, overlays, and intended pane scroll regions remain reachable; controls are not clipped or overlapped; and no unintended document-level horizontal scrolling is introduced.
- At `390×844` and `1440×900`, pointer and keyboard checks cover navigation, current-route state, tooltips, both contact entry points, dialog focus and dismissal, contact submission, toast announcement, and toast dismissal. With `prefers-reduced-motion: reduce`, decorative shell motion stops or becomes effectively instant while state changes and feedback remain perceivable and operable.
- Existing URLs, deep-link behavior, route content, and shell-level interaction outcomes remain unchanged. Route-specific composition and detailed data-visualization styling or motion remain deferred to lifecycle points 5 and 6.
- The browser checks produce no new uncaught runtime errors or unexpected console errors, and `npm run check`, `npx tsc --noEmit`, and `npm run build` complete successfully.

### Known starting condition for tasks 2 and 4: shell heading font-weight gap (confirmed, not fixed)

Independently re-verified against current source (not taken on the orchestrating session's word) that the gap `visual-system-mapping-task.md`'s Known Limitations section already recorded — *"`BootScreen`/`Shell`/`Panes` headings render Sora at ambient weight 400, not `--fw-extralight` (200)... Owner: Route-by-Route Restyling / App Shell Transformation"* — is real and reproducible from source alone:

- `src/features/cv/BootScreen.tsx:61` sets the name heading's className to `font-display text-h3 text-ink-0 leading-[1.05] tracking-display row:text-h2`.
- `src/features/cv/Shell.tsx:92` sets the TopBar wordmark's className to `font-display text-[13px] text-ink-0 tracking-display`.
- `src/styles.css`'s `@theme inline` block (lines 96-105) bridges Tailwind's `text-h3`/`text-h2` utilities to the bare font-size primitives `--fs-h3`/`--fs-h2` only (`--text-h3: var(--fs-h3)`, etc.) — not to the fully-composed `--type-h3`/`--type-h2` shorthand. Tailwind's `font-display` utility (from the separate `--font-display` theme key, styles.css:122-126) likewise sets only `font-family`. Neither className therefore sets `font-weight` at all.
- Critically, substituting the composed role directly would not be a drop-in fix even if attempted: `src/styles/tokens/typography.css:16-17` defines `--type-h3` and `--type-h4` as `var(--fw-semibold) var(--fs-h3)/var(--lh-snug) var(--font-sans)` — a **sans-serif, semibold** sub-heading role, unrelated to the display voice. Only `--type-h2`/`--type-h1`/`--type-hero` (typography.css:13-15) pair `font-display` with `--fw-extralight`. There is no existing composed role that pairs `font-display` + `--fw-extralight` at the `h3` (28px) size — only at `h2` (38px) and above — so `BootScreen`'s base (sub-`row:`) heading size has no ready-made composed role to fall back on; the fix will need an explicit weight applied alongside the existing ad hoc `font-display` + `text-h3`/`text-h2` composition, not a role swap.
- `src/styles/tokens/base.css:2` confirms the ambient fallback these elements inherit: `body{...font:var(--type-body)...}`, and `--type-body` (typography.css:19) is `var(--fw-regular)` (400) — matching the "ambient weight 400" description exactly.
- `.ds-section__title` in `src/styles/ds-components.css:208` has the identical shape of gap: `font-family:var(--font-display);font-size:var(--fs-h4);...` with no `font-weight` declared, and `--type-h4` is the same sans/semibold role as `--type-h3`, so it has the same "no ready-made composed role" property.
- Minor corroborating observation not previously recorded: `Shell.tsx`'s wordmark uses the arbitrary literal `text-[13px]` rather than a token utility. `--fs-body-sm: 13px` already exists in `typography.css:3` and matches this literal's value exactly, but `--fs-body-sm` is not bridged into `styles.css`'s `@theme inline` block (no `--text-body-sm` entry), so no `text-body-sm` Tailwind utility currently exists to reference instead. This is a minor bridge-completeness gap, not a value decision — the value (13px) already exists in the token layer.

This is confirmed as real, in-scope work for later tasks in this subprocess — task 2 for `BootScreen.tsx`/`Shell.tsx`, task 4 for `SectionHeader`'s `.ds-section__title` — and is recorded here as their starting condition. It is **not** fixed by this task, per this task's own scope (verification only, no application source edits). It is not a design decision requiring a stop: the target weight (`--fw-extralight`, 200) and target family (`font-display`, Sora) are already fully decided and implemented elsewhere in the same token layer; what remains is a mechanical CSS composition fix.
