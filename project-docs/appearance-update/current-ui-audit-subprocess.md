# Current UI Audit - Subprocess

## Scope and Deliverable

Begin after Reference Capture is complete, and use the approved **Carry forward / Avoid** section in `project-docs/appearance-update/reference-brief.md` plus `project-docs/appearance-update/project-lifecycle.md` as the visual-direction context. Audit the checked-out application as the authoritative current-state baseline using both source inspection and browser observation. Treat a visible region, reusable component family, interaction, or state as an **audit unit**; individual DOM nodes and repeated instances do not need separate entries unless they behave or need to change differently.

Record the completed audit under an `## Audit Findings` heading in this file. The findings must contain:

- baseline metadata: audit date, commit, relevant uncommitted application-source changes, browser, local server command and URL, exact CSS-pixel viewport sizes, and motion preference;
- a per-route inventory and behavior checklist, with each claim marked **runtime-observed**, **source-confirmed**, or **both**;
- an ownership map from audit units to source files and shared dependencies;
- one disposition and rationale for every audit unit; and
- cross-route themes, route-specific exceptions, risks or unverified states, and explicit handoffs to lifecycle stages 3–6.

Use these dispositions consistently:

- **restyle-only** — the intended direction can be achieved through existing tokens, shared component styles, or route styling without changing markup, state, data, interaction behavior, or responsive/scroll ownership;
- **structural change** — the intended direction requires changes to markup, component composition, state or interaction logic, data flow, or responsive/scroll structure; explain why restyling alone is insufficient; and
- **preserve** — no intentional visual, structural, content, or behavioral change is required, although the unit may inherit project-wide token changes.

### Architectural constraints and invariants

- **Router-only SPA, no server.** `src/router.tsx` builds a single `@tanstack/react-router` client router (`createTanStackRouter`) from the generated `routeTree`; there is no server entry, no API route, no `import.meta.env`/`.env` usage anywhere in `src` (confirmed in the Baseline section), and the only network-shaped call in the app is the browser's own `fetch` of the static `run-4193.webm` file.
- **Deep-linking works, and the app relies on it.** Every screen has a real, reloadable URL — `/`, `/pipeline`, `/replay`, and `/pipeline?run=true` — rather than being a client-only state switch behind one route. `_app.pipeline.tsx`'s `validateSearch` exists specifically so `?run=true` survives a hand-typed URL, a reload, and the back/forward buttons (it normalizes the string form `"true"` as well as the boolean), and `ReplayScreen.tsx`'s "Re-run this dag" is a real `<a>`-rendering `Link`, not a JS-only click handler, so the request survives a middle-click or a copied URL. `router.tsx` also sets `scrollRestoration: true` and `defaultPreload: "intent"`.
- **All data is local and simulated; nothing is fetched.** `src/features/cv/data.ts` (`CV` and everything derived from it) is the single source for the CV's real content; `src/features/cv/live.tsx` (`useLiveSeries`, `RUNS`, `RUN_LOG`, `TICKER`) simulates throughput samples and run history client-side with `setInterval`/`Math.sin`/`Math.random` — there is no query client, no loader, and no backend to point restyled components at.
- **`src/routeTree.gen.ts` is generated and must not be hand-edited.** It is produced by TanStack Router's file-based route plugin from the files under `src/routes/`; any structural route change (new route, new search-param shape) is made in the `src/routes/*.tsx` files and the tree regenerates on the next `vite dev`/build.
- **`src/styles/tokens/` and `src/styles/ds-components.css` are the vendored design-system source of truth — not `src/components/ui/`.** Every `ui/*.tsx` file (`button.tsx`, `dialog.tsx`, `switch.tsx`, `tabs.tsx`, `tooltip.tsx`) says in its own header comment that it was "generated with `shadcn add ...`, then restyled onto `ds-*` classes" — they are thin Radix-behavior wrappers whose visual appearance comes entirely from `.ds-btn*`/`.ds-dialog*`/`.ds-switch*`/`.ds-tabs*`/`.ds-tip__bubble` rules in `ds-components.css`, which in turn reference the custom properties defined in `styles/tokens/*.css`. A restyle should change the token/`ds-components.css` layer, not the `ui/` wrapper files, to keep both shadcn upgrades and Radix behavior intact.
- **Three named responsive breakpoints, not Tailwind's default scale.** `src/styles.css:135-140` clears Tailwind's built-in `--breakpoint-*` scale and defines exactly three: `--breakpoint-row: 540px`, `--breakpoint-split: 850px`, `--breakpoint-console: 1100px`, used throughout the shell and screens as the `row:`/`split:`/`console:` variants (e.g. `Shell.tsx`'s rail/top-bar progressive disclosure, `PipelineScreen.tsx`'s and `ReplayScreen.tsx`'s single-column-to-two-column split). The app is written mobile-first against these three, and `styles.css:187-195` is what makes the body non-scrolling so those breakpoints govern pane-level scroll ownership rather than page scroll.
- **Accessibility semantics already exist in multiple places, not just via Radix.** Beyond the Radix primitives supplying focus trap/Escape (`Dialog`), roving tablist focus (`Tabs`), and switch semantics (`Switch`): `Toast.tsx` uses a native `<output>` (implicit `role="status"` live region); `Card.tsx` promotes a clickable card to `role="button"`/`tabIndex=0`/Enter-Space activation only when it is given an `onClick`; `PipelineNode.tsx` is a real `<button>` with `aria-pressed` and a `sr-only` status prefix ("running:", "completed:", etc.) read before the visible label; `SchemaTable.tsx`'s horizontally-scrolling region is a focusable (`tabIndex=0`) `<section aria-label="Schema columns">` so keyboard users can arrow/scroll it into view; `Input.tsx` wires `label`/`htmlFor` and `aria-describedby` to hint/error text; and `_app.tsx`'s `ContactDialog` explicitly restores focus to whichever of the two Contact entry points (rail icon or top-bar button) opened it, overriding Radix's default trigger-based restoration since neither button is a Radix `DialogTrigger`.
- **Reduced-motion support exists at both the CSS and JS layers, and is incomplete/uneven across audit units.** `src/styles/tokens/motion.css`'s `@media (prefers-reduced-motion: reduce)` block (motion.css:19-23) zeroes `--dur-fast`/`--dur-base`/`--dur-slow` globally and explicitly disables animation on exactly five selectors: `.ds-node--running::after` (pipeline node running pulse), `.ds-ticker__track` (footer marquee), `.ds-spark__head` (sparkline emission-head pulse), `.ds-spark__line--draw` (sparkline draw-on, snapped to its finished `stroke-dashoffset:0`), and `.ds-video__scan` (replay video scanline sweep). Two more reduced-motion checks exist only in JavaScript and are not visible from `motion.css` alone: `useCountUp` in `src/features/cv/live.tsx` (skips the RAF easing for `CvStats`/`CountStat` numerals and snaps straight to the target) and the `scrollIntoView` behavior choice in `PipelineScreen.tsx`'s "Open in inspector" effect (`"auto"` vs `"smooth"`). The pipeline graph's own fit/actual-size zoom relies on `--dur-base` collapsing to `0ms` (a comment in `PipelineGraph.tsx` notes this) rather than a dedicated reduced-motion rule of its own. Task 4 should verify each of these individually rather than assume uniform coverage, since the boot log's line-by-line reveal (`BootScreen.tsx`'s `setInterval`) and the `ds-log__cursor` blink are not among the explicitly zeroed selectors.

### Interaction, Keyboard, and Motion Findings

Method and environment notes, established before the per-route results below and applicable throughout this section: dev server restarted (`npm run dev`, `http://localhost:3000`), same browser pane as steps 1–2. Every claim is tagged **runtime-observed**, **source-confirmed**, or **both**. No application source file was modified; where a check required forcing a failure state or a motion preference, the technique is disclosed inline and was applied at runtime only (live DOM/`localStorage` manipulation in the browser, never a file edit).

Three tooling limitations were discovered during this pass and shape how several results below are worded — recorded once here rather than repeated at each finding:

- **Native Enter/Space button activation could not be triggered through this browser tool's keyboard-dispatch action.** A controlled check (adding a capturing `keydown`/`keyup` listener and inspecting the event) showed the synthetic key press for the space bar arrives with an empty `event.key` **and** `event.code`, and even the correctly-named "Enter" key arrives with a populated `event.key` but an empty `event.code`. The Chrome default action that activates a focused native `<button>` on Enter/Space did not fire for either. By contrast, JS-level handlers that branch only on `event.key` worked correctly once the exact key name was supplied: the boot screen's own `window.addEventListener("keydown", …)` check for `"Enter"` fired navigation correctly, Radix `Tabs`' arrow-key handler correctly moved and auto-activated a tab on `"ArrowRight"`, and Radix `Dialog`'s Escape handler closed the dialog correctly — but the same tool call with the key named `"Return"` or `"Right"` (rather than `"Enter"`/`"ArrowRight"`) produced empty `event.key` values and no effect, confirming this is a tool naming/dispatch quirk rather than an application defect. Consequences below: pointer-click activation and visible keyboard focus are **runtime-observed** everywhere; native Enter/Space activation of plain buttons and switches (the Live Tail switch, pipeline nodes) is **source-confirmed only** — these are real `<button>`/`role="switch"` elements that get platform Enter/Space activation for free per the HTML/ARIA spec and need no app code, but this pass could not exercise that specific path live.
- **Raw pixel-coordinate clicks do not reliably land on target elements.** Screenshots are returned at a different pixel density than the CSS viewport (e.g. 780×1688 for an emulated 390×844 viewport), so coordinates read from `getBoundingClientRect()` (CSS-pixel space) do not line up with clicks issued in screenshot-pixel space. Every click in this pass used an element reference from `find`/`read_page` rather than raw coordinates once this was identified.
- **No reduced-motion (or other) media-feature emulation is exposed by this session's browser tool** — `resize_window` emulates only `prefers-color-scheme` via its `colorScheme` parameter, confirmed by its own documented parameters, and no CDP-level emulation call is available. Reduced-motion checks therefore split into a runtime technique for the app's two JavaScript-level checks (below) and source confirmation for the CSS-only rules, as anticipated by this task's instructions.

#### Resolved: the top-left circular mark

The ownership map flagged an unmapped "circular logo mark" at the top-left of `/` at every viewport. Runtime inspection resolved it: `document.elementFromPoint` on the mark, walked up from the hit `<circle>`, reached a `<button>` with inline styles `position:fixed; top:7.5px; left:7.5px; z-index:99999`, mounted as a direct child of `<body>` — outside the app's own component tree — containing an SVG whose gradient id is `tsd-trigger-mark-cl-0`. This is the **TanStack Devtools floating trigger** (`@tanstack/react-devtools@0.10.12`, via `@tanstack/devtools-ui@0.7.1`), the same component the ownership map already identified in `src/routes/__root.tsx:15-25` configured with `position: "bottom-right"`. The trigger persists its own UI state to `localStorage["tanstack_devtools_settings"]`; that record's `"position"` field also correctly read `"bottom-right"`, but a separate field in the same object, `"triggerCoords":{"x":7.5,"y":7.5}`, pins the trigger to fixed pixel coordinates that win over the named `position` once a user has dragged it (the trigger is user-draggable, per the library's own behavior). Clearing that one `localStorage` key and reloading `/` immediately relocated the trigger to the bottom-right corner, matching `__root.tsx`'s configuration exactly, and it has stayed there for the remainder of this session. Conclusion: the mark is a **runtime/session artifact of a locally-persisted devtools preference — almost certainly left over from a previous audit pass's incidental interaction with the trigger in this shared browser profile — not an application-rendered element and not an application bug.** `index.tsx`, `BootScreen.tsx`, and `__root.tsx` are correctly not responsible for it, exactly as the ownership map suspected. (**both** — runtime root-cause plus the pre-existing source identification of the devtools mount.)

#### Reduced motion (`prefers-reduced-motion: reduce`)

Runtime technique used for the app's two JavaScript-level checks (the only checks a real, unmodified page load makes against `window.matchMedia`, and therefore the only ones this session's tooling could exercise live — see the method note above on why CSS-only rules could not be driven live): `window.matchMedia` was monkey-patched in the already-loaded page so that any query containing `prefers-reduced-motion` reports `matches: true` (a same-realm JavaScript change made through the browser console equivalent, not a source-file edit, and undone by any full page reload); the component under test was then remounted via a client-side SPA navigation (a rail-link click away and back) so its mount-time effect re-ran the check under the patched value; its visible output was sampled on every animation frame for roughly the first 200–900ms to distinguish "already at the final value, no ramp" from "eased in over time." A control run with the same sampling and no patch applied confirmed the method is sensitive enough to detect the normal animated case.

- **`useCountUp` (`src/features/cv/live.tsx:33`), runtime-verified:** with the patch active, the "Pipelines Delivered" `CountStat` numeral read its final value (`"7"`) from the very first sampled frame (t≈0–2ms), with no intermediate values. The unpatched control run showed the expected eased ramp instead (0→1→2→3→4 sampled over ~150ms, consistent with the 760ms ease-out curve in source). Confirms the hook's reduced-motion branch (`if (matchMedia(…).matches) { setN(target); return; }`) fires correctly and the numeral becomes static/instant rather than animating, with no information lost. (**runtime-observed**)
- **`PipelineScreen.tsx:172`'s `scrollIntoView` behavior choice, runtime-verified with a caveat:** with the patch active, sampling `scrollTop` on every frame after clicking "Open in inspector" showed it already at its final value from the first sampled frame, consistent with `behavior:"auto"` (no smooth-scroll ramp). However, this particular load happened to already be pre-scrolled by the intermittent `700×900` issue described above before the click was even made, so this result cannot fully rule out that the pane was already at rest and the click's own call was a no-op. The cleaner, unambiguous confirmation of the same reduced-motion code pattern is the `useCountUp` result above. (**both** — the mechanism is source-confirmed and the observed behavior is consistent with it, but this specific runtime sample is not fully conclusive on its own)
- **CSS-only rules, source-confirmed only** (no way to drive a real `prefers-reduced-motion` media-query match from this session's tooling, per the method note above): the five selectors explicitly zeroed in `motion.css:19-23` — `.ds-node--running::after` (node running pulse), `.ds-ticker__track` (footer marquee), `.ds-spark__head` (sparkline emission-head pulse), `.ds-spark__line--draw` (sparkline draw-on), `.ds-video__scan` (replay video scanline) — plus the global `--dur-fast/base/slow: 0ms` collapse, which also silences the pipeline graph's fit/actual-size zoom transition without a dedicated rule of its own (confirmed in source that `PipelineGraph.tsx:206`'s transform transition duration is literally `var(--dur-base)`, with a comment noting the collapse is intentional).
- **Confirmed gaps, both source- and now runtime-corroborated:** the boot log's line-by-line reveal (`BootScreen.tsx`'s plain `setInterval`, with no motion-preference check anywhere in that file) and its `.ds-log__cursor` blink are unaffected by any reduced-motion setting. Runtime inspection of the live element confirms `.ds-log__cursor`'s `animation-duration` is a hardcoded `1s` string, not one of the `--dur-*` custom properties that collapse to `0ms` under reduced motion — so even the global token collapse cannot reach it, independent of it also not being one of the five explicitly-disabled selectors. (**both**)
- **Static vs. must-remain-available, assessed per the acceptance criteria's distinction:** all five explicitly-covered animations (node pulse, ticker marquee, sparkline head-pulse/draw-on, video scanline) are purely decorative chrome — disabling them removes no state or information, which is the correct target behavior and is what the CSS does. The two uncovered cases are lower-severity than they might first appear: the count-up numerals are now confirmed to already snap correctly (the JS check, not the CSS block, covers them), and the boot log's paced reveal/cursor blink delay *when* four lines of text appear but do not hide any information once shown and do not represent a state change a user could miss — so the gap is a motion-preference consistency issue (the pacing itself keeps running) rather than a case of information disappearing.

### Disposition Matrix

Method: every audit unit named in the Ownership Map (steps 3–4 above) is assigned exactly one disposition — **restyle-only**, **structural change**, or **preserve** — using the Scope and Deliverable section's definitions verbatim. No token values, colors, spacing numbers, or specific visual/markup solutions are chosen below; each entry states only the *kind* of change the intended direction requires and why. Three principles, applied consistently rather than repeated in every row:

1. A unit is **restyle-only** when its entire visual surface resolves to `src/styles/tokens/*.css` values or `ds-components.css` classes it already consumes, with no change to markup, component composition, state, interaction, data flow, or responsive/scroll ownership. Because the app already routes all visual styling for `design/` components and `ui/` wrappers through the vendored `ds-components.css`/`styles/tokens/` layer (see Architectural constraints above), this covers most of the app's surface.
2. A shared `design/` primitive or `ui/` wrapper consumed by 2+ routes (the Ownership Map's "Cross-route shared primitives" table) is dispositioned once at the component level; every route that consumes it inherits that disposition, so per-route rows below do not re-argue the same rationale for, e.g., `Badge` or `LogStream`.
3. Two units carry a genuine **structural change** disposition, both `/pipeline`-only and both already documented as bugs rather than style gaps in the Interaction, Keyboard, and Motion Findings above: the `390×844` node-graph clipping (deterministic) and the `700×900` toolbar-hidden-behind-header auto-scroll (intermittent). Both fail the "achievable via tokens alone" test because their root cause is a fixed/non-reflowing layout dimension and a mount-time scroll-position side effect, respectively — no border, color, spacing, or shadow value changes those.

### Cross-Route Themes and Exceptions

- **The vendored `ds-components.css`/`styles/tokens/` layer is already the single point of restyle, so almost everything is restyle-only.** Every `design/` component and every `ui/` shadcn/Radix wrapper gets its entire visual appearance from this one shared layer rather than component-local styles or Tailwind overrides (confirmed for all 22 `design/` components and all 5 `ui/` wrappers during the Ownership Map pass). This is why 34 of 42 audit units are restyle-only: a token/stylesheet-layer update propagates to every consumer without a markup change. Route-specific exception: none found — this holds uniformly across `/`, the `_app` shell, `/pipeline`, and `/replay`.
- **Fixed-width, non-reflowing content at the narrowest breakpoint is a real, repeated pattern, not a one-off.** The pipeline node graph's 896px intrinsic width against a ~316–325px pane at `390×844` is the clearest case (dispositioned as structural change above), and the same underlying node-graph rendering is what the replay video's paused first frame shows clipped at the same width (since the "recording" is of the pipeline UI itself) — though that second instance is inherited through a video asset, not a live layout, so it carries no separate structural fix of its own. Route-specific exception: `/`'s single-card layout scales down cleanly at all four viewports with no clipping, and `/replay`'s own live UI (as opposed to the video's captured frame) has no analogous overflow beyond the metrics ticker's expected marquee truncation.
- **Reduced-motion coverage is good for continuous/decorative animation but has one real, confirmed gap.** The five CSS selectors explicitly zeroed in `motion.css` and the two JS-level checks (`useCountUp`, the inspector's `scrollIntoView` behavior choice) all correctly target genuinely decorative motion, and one of the two JS checks (`useCountUp`) is now runtime-confirmed correct. The boot log's paced line-by-line reveal and its `.ds-log__cursor` blink, however, are unaffected by the reduced-motion preference at either the CSS or JS layer — a genuine, if low-severity, gap (see rationale in the Architectural constraints section: it delays *when* text appears rather than hiding information). Route-specific exception: this gap is specific to `/`; `/pipeline` and `/replay`'s covered animations are all correctly gated.
- **Two confirmed layout/interaction bugs are independent of styling and must not be conflated with restyle work.** The deterministic `390×844` pipeline-graph clipping and the intermittent `700×900` toolbar-hidden-behind-header auto-scroll are both `/pipeline`-only, both pre-date this project, and both need a code-level fix regardless of whether the appearance update happens. Restyling the affected components will not resolve either. Route-specific exception: `/replay`'s equivalent breakpoints were checked directly and neither issue reproduces there.
- **Accessibility infrastructure (focus-visible rings, focus trap, ARIA roles/labels, `sr-only` status prefixes, roving-tabindex keyboard behavior) is already implemented consistently and confirmed working across the shared shell and both app routes.** This is carry-forward infrastructure, not something the appearance update needs to build — but every restyle-only disposition above that touches an interactive control (buttons, switches, tabs, the dialog, nodes, the video's Play/Pause button) implicitly carries a "verify contrast/visibility of the 2px lime `:focus-visible` outline and glow against the new token colors" follow-up, since the mechanism must survive the restyle unchanged while its color values do not. This is a cross-cutting verification item for App Shell Transformation and Route-by-Route Restyling alike, not a new audit unit.
- **A few pre-existing functional inconsistencies were found that are unrelated to the appearance direction and should not be folded into this project's restyle or structural-change work:** the replay video's `src`/caption not following the selected run, and the Run-duration sparkline's bespoke `Math.sin` simulation versus `useLiveSeries` used everywhere else. Both are preserved as-is for this project (see the Disposition Matrix rows above) and are recorded again under Risks so they aren't lost.

### Risks and Unverified States

- **`700×900` toolbar-hidden-behind-header auto-scroll (`/pipeline`) — intermittent, root cause unconfirmed.** Reproduced once in 5 fresh-navigation attempts in task 4, with figures matching the original report exactly (`scrollTop≈57.5px`). A plausible mechanism (native CSS scroll anchoring reacting to `PipelineGraph.tsx`'s `ResizeObserver` remeasurement) was identified by source inspection but not conclusively verified. Dispositioned as structural change above; recommend re-testing across a larger sample (10+ fresh loads) as part of implementing the fix, since a single spot-check cannot confirm the fix actually closes a ~20% (1-in-5) reproduction rate.
- **Native Enter/Space button activation is source-confirmed only, not runtime-verified, for several controls.** This session's browser-automation tool could not dispatch a synthetic key event that Chrome's native button-activation handling recognized (confirmed to be a tool/dispatch limitation, not an app defect, via a controlled `keydown`/`keyup` inspection). This leaves the Live Tail switch's Space-bar toggle and each pipeline node's Enter-key activation verified only by source inspection (both are standard `<button>`/`role="switch"` elements that get this behavior from the platform/Radix for free). Recommend a follow-up manual or different-tool keyboard check before treating either as fully verified, particularly after Route-by-Route Restyling/Data Visualization and Motion touch `PipelineNode.tsx` or the switch's markup.
- **CSS-only reduced-motion rules (the five selectors zeroed in `motion.css`) are source-confirmed only.** This session's browser tool exposes no `prefers-reduced-motion` media-feature emulation (only `prefers-color-scheme` via `resize_window`), so these could not be driven live; task 4's runtime verification was limited to the app's two JavaScript-level `matchMedia` checks. Recommend a follow-up manual check with a real OS/browser reduced-motion preference enabled before Data Visualization and Motion signs off on any related restyle.
- **The `PipelineScreen.tsx:172` `scrollIntoView` reduced-motion sample is inconclusive.** The one runtime attempt to verify this JS-level check happened to land on a pane that was already pre-scrolled by the intermittent `700×900` bug above before the "Open in inspector" click was made, so the sample cannot fully rule out that the click's own call was a no-op. The `useCountUp` result is a clean, unambiguous confirmation of the same code pattern, but this specific check should be re-run once the `700×900` bug's cause is understood or fixed.
- **Boot log's reduced-motion gap is confirmed, not just theoretical.** Both source inspection (`.ds-log__cursor`'s `animation-duration` is a hardcoded `1s` string, not a `--dur-*` token; `BootScreen.tsx`'s `setInterval` has no motion-preference check) and runtime inspection of the live element agree this is unaffected by the reduced-motion preference. Recorded as a structural/interaction-logic follow-up under the Boot-log panel row in the Disposition Matrix, owned by Data Visualization and Motion.
- **Radix `Tooltip`'s keyboard-focus-triggered display was not independently re-verified at runtime beyond confirming the trigger receives a visible focus ring.** Its focus-triggered open behavior remains source-confirmed only (`ui/tooltip.tsx`, `delayDuration=120`).
- **Replay video `src`/caption does not follow the selected run — a pre-existing, appearance-unrelated data-flow inconsistency.** Selecting `RUN 4192`/`4191`/`4190` in the History panel changes the log transcript and stats but not the video source or its "run 4193" caption text. This is preserved as-is for this project (see Disposition Matrix), but is worth flagging to the project owner separately, since the reference-inspired UI's emphasis on precise, data-rich detail may make this mismatch more noticeable once the surrounding chrome is upgraded.
- **Run-duration sparkline uses a different simulated-data method than the rest of the app.** `ReplayScreen.tsx`'s Run-duration series is a local `Math.sin`-based computation, while every other simulated series in the app (including Throughput on the same screen) uses the shared `useLiveSeries` hook. A code-consistency note, not a visual concern; flagged for a possible separate engineering follow-up outside this project's lifecycle.
- **TanStack Devtools trigger position drift is an environment artifact, not an application risk**, but is recorded here so a future audit pass in the same shared browser profile isn't surprised by it recurring — clearing `localStorage["tanstack_devtools_settings"]` resolves it.
